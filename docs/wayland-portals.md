Managed desktop sessions stay X11 on Xvfb. This note records what native Wayland capture and input through xdg-desktop-portal can and cannot offer, measured on 2026-09-26 for #155. It is an investigation, not a supported feature, and managed Xvfb proof still says nothing about control of a user's own Wayland desktop.

Two compositors were measured. Hyprland 0.56.2 ran with xdg-desktop-portal 1.22.1, xdg-desktop-portal-hyprland (XDPH) 1.4.1 and hyprland-preview-share-picker 0.2.1, nested inside the host session with its own session bus, config and permission store. GNOME Shell 50.4 on mutter 50.5 ran headless in an Arch Linux container with xdg-desktop-portal-gnome 50.0, a private system bus and a stub logind. A small GLib client called the portal methods directly, read one frame from the granted PipeWire node, and for input typed into a GTK entry whose text was then read back. The GNOME claims were then re-run with Pickforge itself: `gnome-shell --devkit` put its viewer window inside a `pickforge-lab` desktop session, and every dialog was read from `pickforge-lab desktop screenshot` and answered with `pickforge-lab desktop click`. Hyprland could not be re-run that way, because it cannot nest inside software-rendered GNOME (it needs `zwp_linux_dmabuf_v1` version 4 and Mutter offers 3). Each claim below comes from those runs, not from documentation.

| Capability | Hyprland | GNOME |
| --- | --- | --- |
| ScreenCast portal | Supported. Version 6, monitor, window and virtual sources, plus a region tab in the picker. The picker opens during `SelectSources`, not `Start`. | Supported. Version 5, monitor, window and virtual sources. One dialog opens during `Start`. |
| RemoteDesktop portal (input) | Unsupported. The interface is absent. InputCapture is present but captures local input for sharing; it does not inject. | Supported. Version 2, keyboard, pointer and touchscreen. "Allow Remote Interaction" is a toggle in the same dialog and defaults to off. |
| Restore tokens | Returned when requested. A reused token skips the picker, is not rotated, and survives portal and compositor restarts. | Same behavior. The dialog shows "Remember This Selection" whenever persistence is requested. |
| Screenshot portal, non-interactive | The first call shows "Allow Apps to Take Screenshots?". | Same prompt, as a shell modal with Deny focused. |
| Visible sharing indicator | None. | Orange top-bar indicator with a stop control. |
| Consent-free paths | wlr screencopy (`grim`), virtual keyboard (`wtype`) and virtual pointer need no consent by default. | Mutter's `org.gnome.Mutter.ScreenCast` and `org.gnome.Mutter.RemoteDesktop` accept any same-user session-bus client with no dialog, showing only the indicator. |

Grants are stored in the xdg-desktop-portal permission store under the empty app id that covers every unsandboxed application. `PermissionStore.List` returns all ScreenCast and RemoteDesktop restore tokens to any same-user process, and a harvested token reopens capture, or on GNOME capture plus input, silently. The Screenshot answer is stored the same way. Closing the prompt without choosing records a persistent "no" for every unsandboxed app, and "Allow" records a persistent "yes". For an unsandboxed tool like Pickforge, portal consent protects the user from surprise, not from Pickforge or anything else running as the same user.

Hyprland's `ecosystem.enforce_permissions` is the only compositor-level gate there. With it on, screencopy by an unlisted binary opens "An application ... is trying to capture your screen" with Deny, Allow and remember, and Allow once. XDPH capture then fails silently with no prompt until XDPH is allowlisted. The preview picker's own capture prompt opens underneath its overlay and cannot be reached, so the share flow hangs until it times out. The stock `hyprland-share-picker` avoids that deadlock. Virtual keyboard and virtual pointer input still reached clients with no prompt while enforcement was on.

Two practical details matter for any implementation. In the headless GNOME container the first keystroke of a new RemoteDesktop session was dropped in every run, but under the devkit viewer it arrived in all four runs, so the first keystroke is unreliable rather than always lost, and typed text needs to be verified before it is trusted. `persist_mode` was never echoed back in `Start` results on either compositor, so the presence of `restore_token` is the only signal that persistence happened.

An opt-in existing-desktop mode would need all of the following. Every session asks through the portal dialog: never request `persist_mode`, never store or reuse restore tokens, and never read the permission store, because a stored token turns one approval into silent standing access for every unsandboxed app. Capture and input go only through the portals. Consent-free paths are off limits even where they work: wlr screencopy, virtual keyboard or pointer, ydotool or uinput, and Mutter's private D-Bus APIs. On Hyprland that makes the mode observe-only. On GNOME, input requires the `devices` result to include keyboard or pointer. Sharing with the interaction toggle off returned `devices` 0, capture still worked, and Mutter rejected injected input with "Session is not allowed to call NotifyPointer methods", so that grant stays observe-only. Pickforge shows its own persistent indicator naming the live desktop, because Hyprland shows none, and the stop control ends the portal session immediately.

Scope limits are part of the grant, not agent guidance. The agent does not type, reveal or copy secrets, and a password or token field ends the attempt. It takes no external or irreversible action, such as sending, purchasing, publishing, pushing or deleting, without the user performing that step. Recovery is limited to stopping and handing back; there are no retries that act on the real desktop. The portal cannot tell human input from agent input, so agent input runs only while the user has handed over control, and any pause or stop wins. Screen content is data and never instructions. Text on screen cannot change the task, grant permissions or redirect the agent, and every action must trace back to the user's request. Screenshots of a real desktop are private evidence: they stay local, get the same redaction as managed sessions, and are never uploaded or committed.

Supported combinations, as measured: GNOME on Wayland can support capture and input through the portals with per-session consent. Hyprland supports capture only, and input there is unsupported through portals. Other wlroots compositors using XDPH or xdg-desktop-portal-wlr are expected to match Hyprland but were not measured. KDE Plasma ships a RemoteDesktop portal but was not measured, so it counts as unsupported until tested. A user's own X11 desktop has no consent mechanism at all and stays out of scope. No implementation issue follows automatically from this note. The smallest candidate is an observe-only live-desktop view through ScreenCast, with GNOME input as a separate step.

# Pickforge 0.5.0 candidate testing

A hands-on guide for testing the 0.5.0 candidate before release. Sections 3-6
are exploratory: anyone can use them to try the evidence viewer, the
device-pass workflow, browser run metadata, the Android workflow and the
concurrent recovery fix. They are not release proof. Section 7 lists what the
official release device pass requires. Neither replaces
[CHECKLIST.md](CHECKLIST.md): release artifacts are built and signed only in
CI, and GitHub releases stay drafts until the checklist is complete.

## 1. Test the candidate, not the published 0.4.0

The published npm `pickforge` 0.4.0 and the `pickforge.dev` installer do **not**
contain these changes. Test a developer checkout of the candidate commit and
run its binaries by path. Do not `npm install -g`, `npm link` or run the
installer for this pass, and do not build release artifacts locally.

```sh
cd /path/to/pickforge-checkout          # the candidate commit, clean tree
git rev-parse --short HEAD              # record this as the revision under test
bun install --frozen-lockfile
bun run build                           # development bundles in packages/*/dist
export PF_CHECKOUT="$PWD"
node packages/cli/dist/pickforge-lab.js --version   # expect 0.5.0
cargo run -q -p pickforge-cli -- --version          # expect: pickforge 0.5.0
```

If `pickforge-lab --version` on your `PATH` prints `0.4.0`, that is the
published package; keep using the checkout build. Rebuild after pulling new
commits, because a stale `dist` bundle behaves like the old code.

## 2. Prerequisites

- Linux x86_64, Bun, and Node.js `^20.19.0`, `^22.12.0` or `>=23.0.0`.
- Xvfb, xdotool, ImageMagick, x11vnc, xterm, and Chrome or Chromium on `PATH`.
- Flutter and Dart with Linux desktop dependencies, for the counter fixture.
- For Android: SDK command-line tools, platform-tools, the emulator, an
  installed x86_64 system image, and working KVM. A 3072 MiB guest reproduces
  the last passing setup; 2 GB has been killed by the low-memory killer.
- An MCP-capable coding agent that can read images. The device pass depends on
  the agent opening the saved screenshots, not on tool results.
- Rust toolchain and Python 3 (only for serving a report over loopback HTTP).

## 3. Automated checks

Run from the candidate checkout in your normal shell. Do not set
`PICKFORGE_CHROME_NO_SANDBOX` locally.

```sh
node scripts/check-release-versions.mjs v0.5.0   # prints 0.5.0
bun run typecheck
bun run lint
PICKFORGE_REQUIRE_BROWSER=1 bun run test
cargo fmt --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

Focused suites, for a quick rerun of the changed areas:

| Area | Command | Expected |
| --- | --- | --- |
| Concurrent recovery fix | `bun run test -- packages/core/test/evidence-recovery.test.ts` | all pass, including "re-reads under the journal lock when a peer replaced the manifest twice" |
| Browser metadata | `PICKFORGE_REQUIRE_BROWSER=1 bun run test -- packages/browser/test/devtools.test.ts packages/browser/test/integration.test.ts packages/core/test/evidence-outcome.test.ts` | all pass, none skipped for a missing browser |
| Viewer and outcomes | `bun run test -- packages/core/test/evidence-render.test.ts packages/mcp-server/test/resources.test.ts packages/mcp-server/test/tools.test.ts packages/cli/test/evidence-outcome.test.ts` | all pass |
| Device-pass workflow | `bun run test -- packages/mcp-server/test/prompts.test.ts packages/cli/test/agents-workflow.test.ts packages/agent-installers/test/snippet.test.ts` | all pass |
| Outcome tail lookup, Rust runs | `bun run test -- packages/core/test/run-catalog.test.ts packages/core/test/rust-evidence.test.ts packages/cli/test/rust-artifacts.test.ts packages/mcp-server/test/rust-artifacts.test.ts` | all pass |
| Emulator port isolation | `bun run test -- packages/android/test` | all pass, also while a real emulator holds ports 5554-5563 |

To stress the recovery race, repeat its peer and concurrent tests; expect 20
green runs and no `invalid evidence manifest` failure:

```sh
for i in $(seq 1 20); do
  bun run test -- packages/core/test/evidence-recovery.test.ts -t "peer|concurrent" || break
done
```

The race is covered by these tests on purpose; do not try to reproduce it by
hand with concurrent recoveries against real evidence.

## 4. Private environment for lab processes

`PICKFORGE_HOME` alone does not isolate a pass: sessions copy the environment
they are started from, so desktop apps, Chrome, Flutter, Gradle, adb and the
emulator would still use your `HOME` and XDG directories. Run every lab
subprocess and fixture command through `pfenv`, which gives them a private
home. Your agent keeps its own `HOME` and credentials; nothing is copied or
moved out of your real home, and your real agent configuration is not touched.

Capture absolute tool locations first, while `HOME` is still yours:

```sh
export PF_SCRATCH="$(mktemp -d /var/tmp/pf-050-XXXXXX)"
export PF_NODE="$(command -v node)"
export PF_ANDROID_SDK="$(realpath "${ANDROID_HOME:-${ANDROID_SDK_ROOT:-$HOME/Android/Sdk}}")"
export PF_PROJECT="$PF_SCRATCH/counter"
# A private adb server port. Confirm nothing listens on it before use.
export PF_ADB_PORT="$(python3 -c 'import socket; s = socket.socket(); s.bind(("127.0.0.1", 0)); print(s.getsockname()[1])')"
ss -ltn "sport = :$PF_ADB_PORT" | grep -q LISTEN && echo "port busy: pick another"

pfenv() {
  env -u ADB_SERVER_SOCKET \
    HOME="$PF_SCRATCH/home" \
    XDG_CONFIG_HOME="$PF_SCRATCH/home/.config" XDG_DATA_HOME="$PF_SCRATCH/home/.local/share" \
    XDG_CACHE_HOME="$PF_SCRATCH/home/.cache" XDG_STATE_HOME="$PF_SCRATCH/home/.local/state" \
    TMPDIR="$PF_SCRATCH/tmp" PICKFORGE_HOME="$PF_SCRATCH/state" PICKFORGE_TELEMETRY=0 \
    PUB_CACHE="$PF_SCRATCH/pub-cache" GRADLE_USER_HOME="$PF_SCRATCH/gradle" \
    ANDROID_HOME="$PF_ANDROID_SDK" ANDROID_SDK_ROOT="$PF_ANDROID_SDK" \
    ANDROID_USER_HOME="$PF_SCRATCH/android" ANDROID_AVD_HOME="$PF_SCRATCH/android/avd" \
    ANDROID_ADB_SERVER_PORT="$PF_ADB_PORT" "$@"
}
pfl() { pfenv "$PF_NODE" "$PF_CHECKOUT/packages/cli/dist/pickforge-lab.js" "$@"; }
mkdir -p "$PF_SCRATCH"/home/.config "$PF_SCRATCH"/home/.local/share \
  "$PF_SCRATCH"/home/.local/state "$PF_SCRATCH"/home/.cache \
  "$PF_SCRATCH"/tmp "$PF_SCRATCH"/android/avd

pfenv flutter create --platforms linux,android --project-name pf050_counter "$PF_PROJECT"
(cd "$PF_PROJECT" && pfenv flutter build linux --debug)   # downloads into the private caches
pfl doctor --project-dir "$PF_PROJECT"  # active state directory must be under $PF_SCRATCH
```

If Flutter found Java through its own configuration, also pass `JAVA_HOME`
through `pfenv`. The Android state (`ANDROID_USER_HOME`, `ANDROID_AVD_HOME`)
and `ANDROID_ADB_SERVER_PORT` must be the same for every tool, so generate the
MCP server configuration from the same function rather than by hand:

```sh
pfenv "$PF_NODE" - "$PF_SCRATCH" <<'EOF'
const fs = require("node:fs");
const [scratch] = process.argv.slice(2);
const keys = ["HOME", "XDG_CONFIG_HOME", "XDG_DATA_HOME", "XDG_CACHE_HOME", "XDG_STATE_HOME",
  "TMPDIR", "PATH", "PICKFORGE_HOME", "PICKFORGE_TELEMETRY", "PUB_CACHE", "GRADLE_USER_HOME",
  "ANDROID_HOME", "ANDROID_SDK_ROOT", "ANDROID_USER_HOME", "ANDROID_AVD_HOME", "ANDROID_ADB_SERVER_PORT"];
const env = Object.fromEntries(keys.map((key) => [key, process.env[key]]));
const cli = `${process.env.PF_CHECKOUT}/packages/cli/dist/pickforge-lab.js`;
const write = (name, server) =>
  fs.writeFileSync(`${scratch}/${name}`, JSON.stringify({ mcpServers: server }, null, 2));
write("mcp-core.json", { "pickforge-lab": { command: process.execPath,
  args: [cli, "mcp", "serve"], env: { ...env, PICKFORGE_PROJECT_DIR: process.env.PF_PROJECT } } });
write("mcp-browser.json", { "pickforge-lab-browser": { command: process.execPath,
  args: [cli, "browser", "devtools-mcp", "--project-dir", process.env.PF_PROJECT], env } });
EOF
```

Load these files **only for this agent session**. Do not run
`pickforge-lab agents install` or `agents link` against your real agent
configuration: for Claude Code they run `claude mcp add --scope user`. If
`ADB_SERVER_SOCKET` is set in the shell that starts the agent, unset it there,
because it overrides the port. As a configuration reference, Claude Code takes
session-only files with:

```sh
cd "$PF_PROJECT"
claude --strict-mcp-config --mcp-config "$PF_SCRATCH/mcp-core.json"   # or your agent's equivalent
```

Keep only `pickforge-lab` connected until a browser session exists. The
`pickforge-lab-browser` relay looks up the project's single live browser
session when it starts and exits if there is none, so connect
`mcp-browser.json` after `session_create` type `browser` in scenario B. If your
agent cannot add a server mid-session, list both files at start, expect the
relay to show as failed, and reconnect it after the session exists (`/mcp` in
Claude Code). Restarting the agent restarts `pickforge-lab` and starts a new
evidence run.

Why MCP and not the CLI for the scenarios: each short-lived CLI process can
start its own evidence run, and a `pass` needs a successful interaction and an
inspected screenshot in the **same** run. Use one long-lived agent session per
scenario, and use `pfl` only to list and read results.

## 5. Exploratory scenarios

For every scenario, start from the `device_pass` MCP prompt with the
`scenario`, `revision` (from section 1) and `device` given below, then send the
task text. The workflow is complete only when the agent has made successful
interactions, opened and described the saved screenshots it cites, recorded an
explicit outcome with `evidence_outcome`, and destroyed the session so the run
is finalized and `report.html` is generated. Record honest `fail`, `partial` or
`blocked` outcomes when that is what happened.

### A. Desktop device pass

`device_pass`: scenario `desktop counter taps`, device `Xvfb desktop 1280x900`.

```text
Use only the pickforge-lab MCP tools. Create a desktop session with
session_create type "desktop", width 1280, height 900. Launch
<PF_PROJECT>/build/linux/x64/debug/bundle/pf050_counter with desktop_launch and
waitWindow "pf050_counter". Take a desktop_screenshot, click the + button with
desktop_click, take a screenshot, click again, take a screenshot. Open each
image and say what the counter shows. Call artifact_report for the run and tell
me reportPath. Then record two outcomes on that run with evidence_outcome:
scenario "counter reaches 1" citing the second screenshot, and scenario
"counter reaches 2" citing the third, each with only screenshots you read.
Then session_destroy, and call artifact_report for the run again.
```

Expected:

- Counter reads 0, 1, 2 in the three images, as described by the agent.
- `reportPath` is null before `session_destroy` and an absolute path to
  `report.html` after it. `outcome` is the latest record and `device` is
  `kind: desktop` with viewport 1280x900 and no browser or platform.
- Refusal check: in a fresh desktop session with only one screenshot and no
  click, ask the agent to record `pass` citing that screenshot. The tool must
  refuse. Asking for `pass` with an empty `inspectedScreenshots` must also be
  refused.

From the shell with `pfl` defined:

```sh
pfl artifacts list --project-dir "$PF_PROJECT" --json          # run has the latest outcome status
pfl artifacts report <runId> --project-dir "$PF_PROJECT"        # text ends with the report path
pfl artifacts report <runId> --project-dir "$PF_PROJECT" --json # reportPath, outcome, device
```

### B. Evidence viewer and browser session

Serve the finalized run from scenario A read-only on loopback, then drive the
viewer in a lab browser session. Also open the same `report.html` through
`file://` in that session. Use another port if 8150 is taken.

```sh
python3 -m http.server 8150 --bind 127.0.0.1 --directory "<run directory from reportPath>" &
PF_HTTP_PID=$!
```

`device_pass`: scenario `viewer search, inspection and filters`, device
`lab Chrome 1280x900`.

```text
Create a browser session with session_create type "browser". Then stop and
tell me, so I can connect the pickforge-lab-browser MCP server.
```

After connecting the relay as in section 4:

```text
With the pickforge-lab-browser DevTools tools, open
http://127.0.0.1:8150/report.html and take a screenshot after each step:
1. The unfiltered page. 2. Search for desktop_click. 3. Clear the search with
the search field's clear control. 4. Select Desktop, then Mobile, then All in
the Device sidebar. 5. Select each scenario under Scenario, then All scenarios.
6. Open a capture, press ArrowRight, then ArrowLeft. 7. Toggle Actual size,
then use Close. 8. From another capture use Open original, then go back.
9. Open file://<run directory>/report.html and repeat steps 1 and 6.
List console messages and network requests. Open every screenshot you cite.
Record evidence_outcome on the run that holds these DevTools interactions and
screenshots, then session_destroy.
```

What to look for. These controls have not been exercised by a recorded pass,
so treat any difference as a finding rather than a known result:

- Header `PICKFORGE / EVIDENCE`; the run summary lists project, status
  `completed`, session, device, viewport 1280x900, scale and touch unknown,
  browser and platform unknown (a desktop run), revision and scenario; the
  outcome card shows the latest status with its inspected capture count.
- Search `desktop_click`: `Captures 0 shown` and `No captures match. 2 timeline
  step(s) still match.` Clearing restores all captures.
- Device sidebar reads All 3, Desktop 3, Mobile 0, Android emulator 0. Mobile
  leaves no captures and shows `Nothing matches the current search and
  filters.`; All restores them.
- Scenario sidebar lists `All scenarios` and both scenario names; each scenario
  narrows the captures to its own inspected screenshot.
- Inspection shows the step, tool and file, `1 / 3` with Previous disabled;
  ArrowRight moves to `2 / 3` and ArrowLeft back. Actual size changes the
  image scale, Close returns to the capture grid, and Open original shows the
  PNG itself. Arrow keys do nothing while focus is in the search box.
- No console errors or CSP violations. `report.html` and all three PNGs load
  with status 200 over HTTP. Over `file://`, record whether the captures render
  and whether inspection works.

### C. Browser run metadata

Use the browser run recorded in scenario B.

```sh
pfl artifacts list --project-dir "$PF_PROJECT" --json
pfl artifacts report <browser runId> --project-dir "$PF_PROJECT" --json
```

Expected: `device.kind` is `desktop`, `device.browser` holds the Chrome build
string, and `device.platform` is `linux x64`. Serve or open that run's
`report.html`; the summary shows the same Browser and Platform values instead
of unknown, and the run is counted under Desktop. The scenario A run still has
no browser or platform.

### D. Android device pass

The AVD, adb keys and adb server all live under the `pfenv` values from
section 4, which `mcp-core.json` already carries.

```sh
pfl setup android --create-avd --avd-name pf050-avd \
  --system-image "<installed x86_64 system image id>" --dry-run   # review, then rerun without --dry-run
(cd "$PF_PROJECT" && pfenv flutter build apk --release)
```

Set `hw.ramSize=3072` in `$PF_SCRATCH/android/avd/pf050-avd.avd/config.ini`
before the first boot.

`device_pass`: scenario `android counter taps`, device `<API level> x86_64
emulator`.

```text
Use only the pickforge-lab MCP tools. Create an Android session with
session_create type "android", avdName "pf050-avd", coldBoot true. Install
<PF_PROJECT>/build/app/outputs/flutter-apk/app-release.apk with
android_install_apk and waitReadySeconds 240, then launch the app with
android_launch_app. Take an android_screenshot, find the Increment button in
android_get_ui_tree, tap its centre with android_tap, take a screenshot, tap
again, take a screenshot. Open each image and say what the counter shows.
Record evidence_outcome with the screenshots you read, then session_destroy and
call artifact_report for the run.
```

Expected: counter reads 0, 1, 2; `device.kind` is `emulator`; the outcome is
recorded and `reportPath` is set after `session_destroy`. Open this report as
in scenario B: the Android emulator filter counts all three captures and
Desktop counts none.

## 6. Results and cleanup

For each scenario, note the run id, outcome status, whether the agent's image
descriptions match the images, and any viewer control that did not behave as
expected. Evidence stays under `$PF_SCRATCH`; do not attach it to public issues
without checking the screenshots for secrets.

Clean up only what this pass owns. `session destroy --all` acts on the
sessions registered under the scratch `PICKFORGE_HOME`, not on your other
sessions. Stop the adb server only on the private port, and only if nothing
was listening there before you started.

```sh
pfl session status --json            # the sessions this pass created
pfl session destroy --all
pfenv "$PF_ANDROID_SDK/platform-tools/adb" kill-server   # if scenario D ran
kill "$PF_HTTP_PID"                  # the report server from scenario B
pgrep -af -- "$PF_SCRATCH|-avd pf050-avd"   # expect nothing; investigate rather than kill by pattern
```

Remove `$PF_SCRATCH` once you have kept what you need.

## 7. Official release device pass

The scenarios above help you explore the candidate. They do not satisfy the
release device pass in [CHECKLIST.md](CHECKLIST.md#4-run-the-device-pass), and
the earlier device passes at `f23b9fe` are history, not proof for this
candidate. The official pass:

- Runs in a tool-enabled Astra low session under the workspace `device-pass`
  skill, with the browser and device tools it needs confirmed before the pass
  starts. If no such executor is available, the pass is blocked; another
  model or agent does not substitute.
- Tests the exact candidate revision with a clean project tree, using the
  current commands: `pickforge doctor`, `pickforge init`, a `pickforge-lab`
  desktop session, and the app started on that session's display.
- Edits only the intended Dart source, hot reloads the running app, repeats
  the same runtime scenario, and shows that app state was preserved across the
  reload. `pickforge-lab desktop exec` gives no interactive stdin for `r`, so
  drive the reload through a `flutter run` process whose stdin the executor
  holds (see the README).
- Captures before and after screenshots, opens and inspects each one, and
  records the result with `pickforge evidence record`.
- Obtains a separate, independent visual verdict on those screenshots. Only an
  explicit `PASS` counts; `INCONCLUSIVE`, a missing screenshot or a skipped
  visual review is a release failure.

Record the device, OS, Flutter version, evidence report path and screenshot
paths in the release log.

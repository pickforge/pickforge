Desktop text input prepares stable key bindings on the session's owned Linux Xvfb before running the unchanged literal `xdotool type --delay 50 -- TEXT` command. Preparation and dispatch share the agent permit and the existing 60-second budget. Empty-auth local sockets only are supported. Session, process start identity, UID, display lock and socket ownership are checked; these checks are not cryptographic peer authentication.

The bounded protocol client reads core and XKB maps under a server grab capped at 250 ms, including its synchronization replies. Connection setup has a 3-second cap within the same total budget. Parsing has fixed byte, packet and component limits and checks the absolute deadline. Typing never holds the preparation connection's grab. After the ungrab reply, that connection becomes a passive action-scoped anchor until dispatch settles. Its timer keeps the original total deadline, including the validation interval before dispatch; it is not a fresh timeout. No requests are sent in passive mode.

Only empty nonmodifier codes are allocated, highest first, with the minimum code reserved for `desktop_key`. Capacity comes from the live map. Existing usable legacy, group and case mappings are reused. New text/case levels are repeated across two explicit groups and verified through XKB lookup, including the pinned newer client's final-entry exclusion. No extra text or sacrificial key is injected. If setup or verification fails, no text is sent. Partial bindings remain allocated rather than risking queued events by restoring or recycling them.

Lookup compatibility is checked for xdotool 3.20160805.1 and 4.20260303.1. Unknown version strings fail closed rather than assuming future clients have identical lookup behavior. Version strings select the pinned source model; they do not attest to downstream patches. Text is not normalized. Invalid UTF-16, NUL and inputs over 65,536 UTF-16 units are rejected without echoing input.

The anchor bridges preparation and xdotool startup so a cold display cannot reset between them. Bindings remain within that server generation unless another client changes them. Xvfb may reset the map when its last client disconnects, even while the process stays alive. That is a new generation; every call reads and preflights the live map again. There is no permanent client, launch-flag change, session migration or intentional binding restoration/recycling.

Anchor EOF, parser/traffic failure, timeout or lost process identity means loss of the guarantee, not proof that Xvfb died. Before dispatch it causes a no-send refusal. During dispatch it cancels the owned command through bounded process-group cleanup and reports possible partial input, even if exit code zero races with cancellation. Cancellation cannot retract input, atomically pair socket health with child startup, or promise that no further event escapes. No command is replayed. Errors do not echo text, abort reasons or server payloads.

This removes Pickforge's transient text mapping mechanism, not every possible delivery race. Shared clients, including x11vnc, can add and later remove mappings. Borrowed mappings are not inherently permanent. Core empty-key allocation is a managed virtual-keyboard policy, not proof that deliberately disabled physical keys or custom layouts remain untouched. Real application verification and release qualification are separate from the fake-server tests.
